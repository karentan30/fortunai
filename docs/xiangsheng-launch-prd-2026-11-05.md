# 相生 Runae：免费内测到正式上线 PRD
版本：2026-11-05。状态：验收目标，不代表全部已实现或已上线。最新用户决定覆盖旧方案：先网页版、默认一张分享海报、暂不做小程序。
## 1. 产品和上线范围
相生是以日主、生肖文化偏好为入口的真实交友工具。主路径：测自己的日主 → 填写本人资料 → 生成单张海报与真实邀请二维码 → 好友扫码进入 → 测自己的日主 → 双方授权基础解析 → 双方另行同意文字聊天；认识申请与自愿交换联系方式作为平行路径。
日主/生肖是用户可修改的兴趣筛选，不预测婚姻成功、怀孕年份或财富。不得用AI照片、虚构高资产资料填充真实人库。

P0 免费内测：生日表单、注册登录、资料保存/编辑/撤回、个人页、单图导出、真实二维码、邀请上下文、双方申请接受、隐私/屏蔽/举报/删除、基础推荐、状态与错误提示。
P1 收费：服务端额度账本、月会员、年会员、单报告订单、支付通知校验、权益开通、退款、双方授权的真实报告交付。
P2：内置语音、场馆订位、多人活动、AI语音访谈、小程序、商家分佣。P0不承诺这些功能。

## 2. 页面与表单
首页极简：品牌“相生 · Runae”；“测测你的日主，认识五行合拍的人”；测日主主按钮；可辨识的虚构样例卡；生日表单。
表单：公历/农历明确选择，年月日中文标签；出生城市（支持境外）；小时分钟一起输入、无秒；时间不确定可选未知；真实出生信息与身份证登记日期可不同，身份年龄认证独立。未知时辰不制造时柱，完整报告标出影响。
访客可先填写；保存到后台前登录并单独确认保存/公开/匹配用途。拒绝公开不妨碍查看自己的结果。不得通过扫码自动把人加入公开人库。

样例：知远，29岁 / 180cm / 75kg，北京大学·博士，AI算法工程师；家庭资产A9.3。样例所有资料为虚构。个人资产不得混入家庭资产。

## 4. 扫码邀请与双人分析
公开个人卡二维码使用不可枚举的分享标识，不编码生辰。链接包含合法白名单来源和campaign用于聚合转化。
扫码后首屏展示邀请者公开名片与“测测我和TA的五行”；登录前保留邀请上下文，登录后回到原邀请，不错误绑定到其他人。
邀请者必须选择用途：公开认识入口/指定双人分析。公开分享码与双人授权令牌分离。撤回、过期、删除、屏蔽后入口不能继续泄露资料。
访客A/B均单独录入或授权自己的资料；仅在双方同意后生成指定范围的双人结果。先到者看等待状态，不能借报告推算另一方生日。撤回后禁止新生成和新分享，界面明确已下载内容无法远程删除。
两人都同意认识后才自愿交换微信；接受申请免费。付费不能跳过对方同意。重复申请不扣第二次，屏蔽后禁止互相推荐和申请。
完整报告和文化简版明确区分，不能把日主单一关系包装为完整合盘。样例页 pages/friends-report-sample.html 为虚构结构演示，不可当作实际用户计算结果。

## 5. 推荐规则与透明解释
目标规则：先双向必要条件（成年人、目的、性别偏好、年龄范围、城市），再排序用户明示的日主/生肖偏好、共同爱好和可用时间。当前实现仅基于已公开日主/生肖、共同爱好与认识目的排序，支持城市筛选；尚不能宣传已完成双向性别/年龄偏好筛选。偏好权重可调，不以五行判定人品/财富/生育。
拒绝、屏蔽、已认识、过期/停用、未授权公开的用户排除。没有候选就说明暂无，允许扩大偏好，禁止假用户或重复凑配额。
推荐理由来自可授权展示的字段，如同城、共同活动与对方愿意认识的类型，不能暗示已验证所有资料。质量指标为双向接受与满意反馈，不以注册量或伪造的“婚姻分数”代替。

消息纯文本、最多1000字、带服务端身份与时间；客户端随机幂等ID防网络重试重复发送；分页、频率和总量有服务端上限。话题按钮只填草稿，发送由本人点击。没有AI代发、语音、视频、在线状态或已读承诺。轮询只在有效当前会话可见时进行；切换账号/会话/撤回清除显示并拒绝旧响应。

## 14. 本轮产品闭环冻结与修复验证
本节是当前优先级与验收合同；“需修复”不代表已合入或已部署。用户目标：先用日主认识人，重点突出、操作简洁；不是先填长表，也不是付费后才能看到真实服务。

### 14.1 两种入口、一个下一步
| 当前页面/状态 | 用户看到什么 | 主操作与下一站 | 不应发生 |
|---|---|---|---|
| 首页访客 | 公历/农历、年月日、出生城市、小时分钟或未知 | 免费测日主 → 结果 | 未授权保存原始生辰、强制先注册 |
| 结果 | 自己日主、文化偏好推荐、可修改选择 | 制作我的分享卡 | 将推荐说成命定对象、保证互旺 |
| 匿名日主卡 | 日主和自选亮点；清楚说明扫码只测自己 | 保存图片；或完善个人资料 | 宣称匿名卡已在好友库展示 |
| 资料草稿 | 精简个人亮点、公开范围与是否加入发现 | 登录后本人重新确认保存 → 个人卡 | 登录自动公开、丢草稿、混入上一账号草稿 |
| 私密个人卡 | “仅自己可见”、公开加入入口 | 自愿开启公开后，才能生成对应公开认识入口 | 链接绕过隐私读取卡片 |
| 已公开个人卡 | 用户允许公开的资料与真实二维码 | 保存分享 → 对方扫码看该卡 | 二维码出现原始生日或私人联系方式 |
| 扫码访客 | 邀请者公开昵称与卡片、两个明确选择 | 测自己，或邀请对方看双方基础解析 | 测完/注册后丢失邀请者上下文 |
| 发现页 | 真实公开候选及可解释偏好；无候选诚实为空 | 查看卡片 → 发起双人解析或申请认识 | 示例冒充用户，曝光未公开信息 |
| 认识申请 | 待处理/已接受/已拒绝/已解除 | 已接受后可明确进入该人的双人邀请；双方有意再授权 | 把接受认识等同授权生辰、聊天或自动交换微信 |
| 双人定向入口 | 对方公开昵称、查看对方卡片、基础解析用途 | 确认发起 → 填本人信息与本次授权 | 仅显示难以理解的shareId、邀请错人 |
| 双人基础解析 | 依据与缺失说明、文化线索、双方授权的补充话题 | 双方自愿开启文字对话 | 诱导付费获取尚未实现的完整报告 |
| 双人文字对话 | 本人/对方消息、草稿话题、有效期限与撤回入口 | 自己编辑并发送；继续了解 | AI冒充真人发送、默认接受聊天 |
| 任一步失效 | 明确撤回/到期/删除/屏蔽状态与可行返回入口 | 回我的邀请或发现 | 持续显示旧私密报告或旧消息 |

导航最小闭环：个人卡 / 找朋友 / 认识申请 / 双人邀请。双人页须能返回个人卡和发现；返回不要求重复输入全部生辰。登录状态保留但生日原文不因方便而写入URL或不受控本地缓存。已有保存授权才可读取私密建档，不能默认复制对方资料。

### 14.2 双人邀请逐状态主操作
每个状态只突出当前能做的一步；未满足条件的动作解释原因，不笼统显示“待解锁”。

| 状态 | 发起人下一步 | 接收人下一步 |
|---|---|---|
| 新建、本人未授权 | 填写本人出生信息并确认本次授权 | 尚未收到可用信息时不展示对方私人资料 |
| 本人已授权，开放邀请尚未认领 | 复制邀请链接发给想了解的人 | 注册/登录自己的账号并自愿认领 |
| 开放邀请已认领，待发起人确认 | 核对自报昵称后确认接收人 | 等待对方确认；昵称不代表身份核验 |
| 定向邀请/已确认、缺一方授权 | 已授权者等待；未授权者补充自己的授权 | 同左 |
| 双方基础解析已就绪、聊天未双同意 | 查看基础解析；说明聊天需另行同意 | 同左；不同意聊天也能看基础解析 |
| 双方独立同意聊天 | 查看解析/开始或继续对话 | 同左 |
| 过期、婉拒、撤回、不可用 | 清除私密展示；回邀请列表或重新发起 | 清除私密展示；返回自己的入口 |

开放邀请token只在创建时提供；刷新后链接无法找回时明确说明“撤回后重新邀请”，不可假装能恢复。定向卡片已绑定接收人，不要求多余的开放邀请认领。不会自动发送给任何人。

### 14.3 本轮仅修三个P0断点
1. **已认识后接不上双人解析/聊天**：认识申请列表增加针对该人的明确入口，主导航与双人页提供往返。不能直接把接受认识视为基础解析或聊天授权。验收：A申请B→B接受→A/B能从列表明确找到同一对象的解析入口；拒绝聊天仍可读基础解析。
2. **定向邀请缺对象确认及状态引导**：公开卡进入target页时显示实际公开昵称与回看卡片入口；服务器仍负责归属权限。逐状态标出当前下一步；只读公开信息失败则禁止假装已确认目标。验收：甲卡进入只邀请甲、登录后仍是甲；不存在/私密卡清晰报错，不能悄悄变成开放邀请。
3. **分享完成不等于已加入认识人库**：导出前解释本次二维码究竟跳转“测自己的日主”还是“查看我的公开卡”；明确个人卡公开状态，提供自愿完善资料入口。验收：匿名卡扫码只进入测试且不新增公开用户；公开个人卡扫码进入正确用户；用户撤回公开后旧码不能继续读卡。

以上由产品指定验收、开发提交修复、独立测试复核；不再同时增加场馆、收费、语音、长表AI访谈等新功能。

### 14.4 修复—测试—回看循环
每条P0记录：复现前置状态→修复提交→自动检查→两账号人工操作→证据→关闭/仍待解决。任何失败回到该条修复，不以总测试数替代场景通过。

自动回归至少覆盖：
- 匿名测算/匿名卡与公开卡的链接目的不同；QR链接不含出生参数。
- 原卡片邀请者上下文穿过测算、注册、保存后仍正确；私密/删除/不存在卡不会误引导新邀请。
- 认识接受后的双人入口带正确目标；反复点击不自动产生多份授权。
- 双方邀请每个状态有下一步；没有chatConsent时看报告成功、聊天API不调用。
- 撤回、到期、账号切换、解除认识后无旧消息/旧报告残留，旧异步响应不重新渲染。
- 320/390/768/1440宽度无溢出；长昵称、空候选、服务关闭、网络失败可恢复。

上线前人工验收必须用两个本人控制的真实内测账号，在iOS/安卓微信里完成：测日主→保存一张个人卡→扫码→确认正确人→双方分别授权→读基础解析→分别同意聊天→双方发送→撤回。邀请接受与双人解析是两条不同权限链，各测一次。原站登录/个人报告路径同时做回归，不能因新功能破坏原业务。

### 14.5 真实能力与上线口径
当前代码有确定性日主/生肖规则、公开卡、邀请、双方授权的基础关系指南与独立同意文字聊天；这是代码能力，生产仍须安装对应增量、启用白名单并完成上述真机闭环。聊天只做文本，没有已读/即时推送/语音承诺，邀请有效期不是永久聊天存档。
公开样例用于看展示结构，不能把特定示例的“两组合”写成所有真实用户结果。当前真实基础解析不等于喜用判断或收费AI完整合盘，不能承诺子女缘/结婚年份/成功率。
会员与新双人详细报告依然关闭真实销售；不因基础指南和文字聊天上线而解除该限制。对外文案统一用“免费内测”“基础关系指南”“双方同意后开始对话”，避免“匹配完成”“全盘已生成”“已找到最佳对象”等超过实际能力的说法。
