## 1. 🔴 我推翻了自己的一条结论（重要，先说）

我在核查过程中一度判断「Stripe webhook 挂了、付费用户拿不到东西」，**这个判断是错的，我自己证伪了**：

- 起因：日志里有 19 条 `[WEBHOOK SIG ERR] No signatures found matching the expected signature for payload`，且 `[PAYMENT]` 成功日志为 0。
- 证伪：按天统计订单状态发现——**08-09 之后每一笔订单都正常走到了 `expired`/`completed`**，`expired` 只在 webhook 正常工作时才会被写（`payment.js:373` 是唯一写入口）。若 webhook 真挂，08-09 之后的单子会一直卡在 `pending`。
- 复验：无签名 POST → 400；伪造签名 POST → 400；`GET /api/.env` → 404。
- **结论：webhook 是健康的。那 19 条是外部扫描器往公网端点发垃圾 POST，被正确拒绝了。**

保留这条记录是因为：如果只看到「19 条验签失败 + 0 条成功」，很容易误判成 P0 线上故障并去做无谓的紧急处理。

## 2. 本轮做完（未部署 · 分支 `work-0911`）

### 2.1 支付：堵住「支付宝 + 订阅」的组合（`03cc8a5`，cherry-pick 自 0909 分支）
- 新增纯函数 `server/lib/stripe-methods.js`：`resolvePaymentMethods(methods, isSubscription)`。
- 问题：`payMethods`（来自请求体 `region`/`currency`）与 `isSubscription`（来自 `product`）各自独立计算，
  于是**非大陆 IP 发 `region:'cn'` + 会员商品**会得到 `['card','alipay']` + `mode:'subscription'`。
  Stripe 的支付宝/微信只支持一次性付款 → 请求被拒 → **500**。
- 现在订阅单自动降级为 `['card']` 并 `console.warn` 留痕。9 条单测通过。
- **仍需你在 Stripe 后台做的事**：见该 commit 里的「后台开通清单」（支付宝/微信支付方式要在 dashboard 里实际打开，否则降级后用户只剩卡可选）。

### 2.2 安全：三处「看起来有防护、实际没生效」（`fc8fc53` + `a24ccb8`）

**(a) 限流白名单只有 13 个前缀，站上已有 40+ 路由。**
后来新增的 `numerology` / `life-kline` / `chart-archetype` / `identity-triad` / `western-astrology` /
`best-timing` / `love-destiny` / `hepan` / `support-chat` / `shouxiang` / `duanshi` 等等
**全都写了 `rateLimitMiddleware` 却完全不生效**——中间件第一行就 `return next()` 了。
白名单式防护天然随新增路由腐化 → 改成 **`/api/*` 默认拒绝 + 显式豁免**，新增路由自动受保护。

**(b) 中间件被挂了两次。** 全局挂 1 次（`index.js:87`）+ 各路由挂 89 次，
同一次请求计两次 → **实际限额只有标称的一半**（匿名 75/h 而非 150/h）。
加 `req._syRateCounted` 幂等标记。

**(c) 🔴 补测试时立刻抓到一个会真出事的 bug：支付回调根本没被豁免。**
豁免名单里写的是 `'/api/pay/'`（带尾斜杠），但匹配规则是
`path === prefix || path.startsWith(prefix + '/')` —— prefix 带尾斜杠时第二个条件变成
`startsWith('/api/pay//')`，**永远为假**。
于是 `/api/pay/wechat/notify`、`/api/pay/alipay/notify`、`/api/pay/*/query`
这些**钱路全部落在限流范围内**。后果是「用户付了钱 → 回调被 429 → 不发货」，
且微信/支付宝会重试、重试同样被拒，订单永远到不了 `completed`——**静默且极难归因**。
改成 `'/api/pay'`（不带尾斜杠）。

**(d) 排行榜页会被打挂。** `pages/leaderboard{,-en}.html` 每 10 秒轮询
`/api/referral/leaderboard` + `/api/referral/mine`（360 次/小时 × 2 接口）。
旧白名单模式下这两个压根不受限；改默认拒绝后**约 12 分钟就会开始 429**。已加豁免（只读、不烧 LLM）。

**(e) 免费额度可被客户端重置。** 配额 key 原本是 `(uid || sessionId || ip)`，
而 `x-session-id` 是**客户端自己发的 header**，前端总会带上 → uid 为空时永远走 sessionId 分支，
**每次请求换个随机值即可重置配额**，免费额度形同虚设。
改为只认服务端可控的 `(uid || ip)`。涉及 8 个路由：
`numerology` / `oracle` / `life-kline` / `iching-en` / `daliuren-en` / `qimen-en` / `ziwei-en` / `daily`。

**(f) `ADMIN_TOKEN` 未设时的放行。** `email.js` 三处 + `push.js` 一处只写了
`token !== process.env.ADMIN_TOKEN`；若 env 未设，两边都是 `undefined` → **不带 token 的请求反而能过**。
加 `!process.env.ADMIN_TOKEN ||` 短路。**生产当前有设 ADMIN_TOKEN，属纵深防御，不是线上可利用漏洞。**

**新增测试 `server/middleware/rate-limit-scope.test.js`（8 条）** 钉住「哪些路径受限」：
钱路红线、轮询豁免、AI 路由必须受限、新增路由默认受保护、前缀段边界（`/api/payroll` 不能被 `/api/pay` 蹭到豁免）。
> 另：清理定时器加了 `.unref()`——它把事件循环钉住，导致任何 `require` 中间件的 `node --test` 都会永远挂住
> （上面那组测试一开始就是这么卡死的）。生产无影响。

# 第三轮（0911 深夜 → 0912 凌晨）：页面写的价 ≠ 实际扣的价

## 14. 这一轮的核心发现：线上根本没有固定价格 ID，目录是唯一价目表

核实过的事实：生产 `.env` **没有 `STRIPE_PRICE_IDS` 这个键**（进程内长度 0，不是解析失败）。
所以 `routes/payment.js` 里

```
const priceId = (!isMonthlyDiscount && (STRIPE_PRICE_IDS[currKey] || STRIPE_PRICE_IDS[product])) || null;
```

永远取到 `null`，**一切结账都走 `price_data`，实收金额 = `PRODUCTS[key].amount`**。

结论：**`store.js` 的 PRODUCTS 表是唯一价目表**。而页面文案是手写的，历次调价后逐页漂走，
于是出现「用户看到的价」和「实际扣的价」不一致——**两个方向都是事故**：
收多了是投诉/合规，收少了是白送。这类漂移**没有任何报错**：支付成功、订单入库、
页面提示已解锁，只有账单上那个数字不一样，真浏览器走查和 curl 探活都测不出来。

# 第二批（0912）：前端调了一个不存在的接口 —— 一类静默失败的普查

## 22. 这一轮怎么找到的

上一轮修「价格漂移」时立的守卫都是**静态比对两边**。顺着同一个思路再往前走一步：
「前端 fetch 的路径」和「服务端注册的路由」是两套手写的名字，**它们对不上时会怎样？**
答案是 404 —— 而 404 在页面上几乎永远表现为「点了没反应」「表单一直失败」「列表一直是空的」，
**没有任何报错**。UI 冒烟测不出（它只看页面能不能渲染、不点每个按钮），
curl 探活也测不出（得先知道该探哪个路径）。

于是新增守卫 `server/lib/frontend-calls-have-routes.test.js`：
**基准取 Express 运行时自己的路由表**（require index.js 前劫持 `app.use` 记挂载前缀，
再遍历 `router.stack` 里的 `layer.route.path`），不重新实现一遍路由解析。
抽出 `pages/*.html` 里所有 `/api/...` 字面量逐一比对，区分「写死的路径」（必须精确存在）
和「拼接的路径」（如 `'/api/invite/' + code`，只要求这条路由族存在）。

**第一次跑就抓到 9 条线上 404**，并用 curl 逐条在生产上确认过（9/9 都是真的 404）。

### 23.1 account.html 那四个（最有欺骗性）

`routes/profile.js` 和 `routes/subscription-history.js` **文件一直都在**，
`ls server/routes/` 看得见，但 `index.js` 从没 require 过它们 —— 「文件在、路由不在」，
光看目录结构完全看不出来。而且 `profile.js` 是 **SQLite 时代的残留**：
写的是 `store._M.db.prepare('UPDATE users ...')` 和 `DELETE FROM sessions`，
而本项目 store 是 JSON 快照，没有 `.db`、也没有 `sessions` 表 —— 就算挂上去也是 TypeError→500。
所以是「三重坏」：没挂载 + 写错数据层 + 前端把任何非 2xx 都显示成「当前密码错误」。

修法：`lib/store.js` 补三个真实可用的数据访问口（`getUserPrivateById` / `updateUserFields` /
`deleteUserTokens`），`profile.js` 与 `subscription-history.js` 按 JSON store 重写，`index.js` 挂载。
- `getUserById` **故意没有**加 birthday/gender/password_hash —— `/api/auth/me` 也在用它，
  返回 `password_hash` 等于把口令哈希发给前端。
- 改密码只踢**其他设备**（保留当前这条 token）：全踢的话用户刚点完「密码已修改」就发现自己退登了。
- 订阅历史原来还把 `amount`（**分**）当元返回，前端 `'¥' + h.amount` 会把 ¥299 显示成 ¥29900；
  且 `amountCents` 的**单位随通道变**（微信/支付宝是人民币分、Stripe 是美元分），
  所以改成服务端算好带币种的 `amount_text` 再给前端。

### 23.2 life-events.html 的预约表单

11 个报告页/落地页链到这个页面，它的「预约咨询」表单**点了永远是提交失败**。

| 改密码全流程 | 改前两台设备都 200 → 改后当前设备 200、另一台 401 → 新密码能登录、旧密码 401 |

## 25. 本轮其他发现（未修，等你定）

- **duanshi.html 的付费墙是装饰**：按钮是 `alert('即将开放，敬请期待')`，没有接结账，
  所以**没有「收钱不给货」的风险**。但服务端 `/duanshi/stream` 从不返回 `paywall`，
  前端 `showPaywall` 永远不会触发 —— 修完路径后用户**免费用**整套断事解读，
  而页面上写着「解锁完整卦象 ¥9.9」（目录里 `duanshi_full` 是 $29 / ¥59）。
  要不要真接付费墙、以及定哪个价，是定价决策。
- `saju-KR.html` / `/pay/stripe/create` 缺 KRW/CNY 分支、`public/geo-pricing.js` 第二份价目表、
  年费三价冲突 —— 同上一批第 19 节，仍未动。
- 服务器端**没有任何登出接口**：account.html 的「登出所有设备」其实只清了 localStorage，
  服务端 token 一条没删（这也是为什么改密码那条要单独处理踢人）。

## 26. 一句话总结

9 条全修好，本地端到端逐条验过（改密码连多设备踢人都验了），52/52 单测通过。**
